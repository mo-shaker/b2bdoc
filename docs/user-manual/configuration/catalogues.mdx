## What the catalogues are for

Four shared vocabularies that answer four planning questions:

| Catalogue | Question |
| --- | --- |
| **Capacity Profiles** | How much can this vehicle carry, in which dimensions? |
| **Handling Profiles** | How must these goods be handled? |
| **Compatibility Groups** | What may not travel together? |
| **Shelf-Life Profiles** | How much remaining life must these goods have? |

## Capacity profiles
<Screenshot
  src="user-manual/20-capacity-profiles.png"
  alt="The SCOP Capacity Profiles list."
  caption="Capacity profiles on b2b. A vehicle without one is invisible to planning."
/>


`SCOP → Master Data → Capacity Profiles`

The dimensions a vehicle is measured in, and its limit in each.

| Field | Meaning |
| --- | --- |
| **Name** | What the profile is called |
| **Code** | A short reference |
| **Dimensions** | One line per measure, each with a **maximum value** and whether it is **mandatory** |

Verified on `b2b`: the demo truck profile declares `weight_kg` up to 4,500 and `volume_m3`
up to 22, both mandatory.

Typical dimensions are **weight** in kilograms and **volume** in cubic metres.

:::danger[This is the one catalogue that is not optional]

A vehicle with **no capacity profile is invisible to planning.** The provider filters to
vehicles that declare one.

If every demand comes back *No feasible vehicle*, check this before anything else.

→ [Fleet and Vehicles](./fleet-and-vehicles.mdx)

:::

Capacity is validated at **every point of the stop sequence** — see
[Trips](../execution/trips.mdx).

## Handling profiles

`SCOP → Master Data → Handling Profiles`

How a product must be handled: refrigerated, frozen, fragile, hazardous, upright.

| Applied to | Meaning |
| --- | --- |
| A **product** | These goods need this handling |
| A **vehicle** or **compartment** | This can provide it |

A handling profile carries the physical facts — **temperature control** with a minimum and
maximum, a **hazard class**, whether the goods are **fragile** or **stackable**, the
**maximum stack height**, and whether they must be kept **upright** — plus the
**compatibility groups** it belongs to.

Planning matches the two. A shipment needing refrigeration is not placed on a vehicle that
cannot provide it.

:::note[An empty handling catalogue means handling is not considered]

If no product declares a handling profile, nothing is matched and nothing is refused. That is
correct for a deployment where handling genuinely does not vary.

Add profiles when a real constraint exists, not to be thorough.

:::

## Compatibility groups

`SCOP → Master Data → Compatibility Groups`

What may **not** travel together.

| Field | Meaning |
| --- | --- |
| **Name** | The group |
| **Code** | A short reference |
| **Separation Level** | How far apart the goods must be kept — see below |
| **Incompatible With** | Which other groups it may not share space with |

Membership is declared from the **other** side: a **handling profile** names the
compatibility groups it belongs to, not the reverse.

### The three separation levels

| Level | Means |
| --- | --- |
| **Separate vehicles** | The goods may not travel on the same vehicle at all |
| **Separate compartments** | One vehicle is fine, provided each has its own compartment |
| **Separate pallets** | One compartment is fine, provided they are not stacked together |

Choosing the weakest level that is actually true matters: declaring *Separate vehicles*
where *Separate pallets* would do turns one trip into two.

A demand that cannot join a load because of an incompatibility comes back unplanned with
*Product incompatibility*.

:::info[Incompatibility is symmetric]

Declaring group A incompatible with group B means neither may travel with the other. You do
not need to declare it twice.

:::

## Shelf-life profiles

`SCOP → Master Data → Shelf-Life Profiles`

Remaining-life rules for a product: how much life must remain at dispatch, or on arrival.

| Field | Meaning |
| --- | --- |
| **Total Days** | The product's full shelf life |
| **Min Remaining Days on Delivery** | How much life must be left when it reaches the customer |
| **Blocking** | Whether falling short stops the movement, or only records it |

:::note[Shelf-life is not enforced as a planning refusal in Release 1]

The profiles are recorded and available. Release 1 does not refuse a plan on remaining life.

If shelf-life is an operational control in your business, treat it as a warehouse
responsibility today.

:::

## Which catalogues you actually need

| Catalogue | Needed when |
| --- | --- |
| **Capacity Profiles** | **Always.** Planning cannot work without them |
| **Handling Profiles** | Goods genuinely differ in how they must be carried |
| **Compatibility Groups** | Some goods genuinely may not travel together |
| **Shelf-Life Profiles** | Goods have expiry dates that matter operationally |

:::warning[An empty catalogue is not a gap]

Three of the four are optional. Populating them "for completeness" adds constraints planning
must satisfy, and every unnecessary constraint is a demand that comes back unplanned.

Add a profile when a real rule exists.

:::

## Verify

| Check | Where | Expect |
| --- | --- | --- |
| Every planning vehicle has a capacity profile | The vehicle | **Planning Ready** true |
| Handling needs are matched | The trip | The right vehicle for the goods |
| Incompatible goods are separated | The trip's contents | Not on one vehicle |
| Nothing is over-constrained | `Planning → Unplanned Demand` | Few *Product incompatibility* rows |

## If it does not work

| Symptom | Cause | Fix |
| --- | --- | --- |
| Every demand comes back *No feasible vehicle* | No vehicle has a capacity profile | Assign one |
| Demands come back *Product incompatibility* | An incompatibility excludes every combination | Check whether the rule is real, or plan them separately |
| A vehicle is never offered work it could do | Its handling capabilities do not cover the goods | Add the capability |
| Incompatible goods travelled together | Neither product declares a handling profile in a group | Declare them |
