**Role**
Operations Manager authorises. Planner proposes.

## The rule

:::danger[The person who creates a plan cannot approve it]

`BR-PLN-001` refuses **approval** and **release** by the plan's own author.

**This includes an Administrator.** Administrative rights and approval authority are
different things, and one does not confer the other.

:::

## Why

A plan commits vehicles, drivers, warehouse labour and customer promises for a whole day.
One person proposing it and the same person authorising it means nobody actually checked it.

The check is not bureaucracy — it is the only point in the cycle where somebody who did not
build the plan reads the unplanned demand and asks whether today's choices are acceptable.

:::warning[A team of one cannot complete a SCOP cycle]

This is intentional, not an oversight. Testing SCOP requires at least two accounts: a
planner and an approver.

:::

## How it is enforced

Two mechanisms, working together.

| Mechanism | What it does | Where |
| --- | --- | --- |
| **`BR-PLN-001`** | Refuses approval and release by the author | Fires at `plan_approve` and `plan_release` |
| **Approval authority** | Requires the actor to hold the entitled group, with **Forbid Self-Approval** set | `Governance → Approval Authorities` |

```text
scop.plan  ·  approve  ·  Operations Manager  ·  Forbid Self-Approval = Yes
scop.plan  ·  release  ·  Operations Manager  ·  Forbid Self-Approval = Yes
```

Both must be satisfied. Holding the group is not enough if you wrote the plan; not writing
the plan is not enough if you do not hold the group.

## Who can approve

| You are | Can you approve a plan you created? | Can you approve someone else's? |
| --- | --- | --- |
| Planner / Dispatcher | No | **No** — you do not hold the authority |
| Operations Manager | **No** | **Yes** |
| Management | No | No |
| Administrator | **No** | Yes |

## BR-PLN-002 — a blocked trip is not released with its plan

| | |
| --- | --- |
| **Code** | `BR-PLN-002` |
| **Name** | A blocked trip must not be released with its plan |
| **Severity** | **Blocking** |
| **Fires at** | `plan_release` |
| **If it cannot be evaluated** | **Block** |

A plan is released as a whole. If one trip on it carries a blocking finding — most often a
capacity breach under `BR-RTE-001` — releasing the plan would put an infeasible trip into
operation alongside the good ones.

`BR-PLN-002` refuses, and **names the offending trip**.

| Fix | How |
| --- | --- |
| Repair the trip | Reduce its load, change the vehicle, resequence the stops |
| Remove it from the plan | Its demands return to **Eligible for Planning** |
| Then release again | The rest of the day proceeds |

## The trip rules

Trips carry their own rules, evaluated when a trip is approved or released.

| Rule | Severity | Checks |
| --- | --- | --- |
| `BR-RTE-001` | **Blocking** | The load is feasible at **every point** of the stop sequence, not only at departure |
| `BR-RTE-002` | **Warning** | Vehicle utilisation is not wasteful |

:::info[Why capacity is checked at every point]

A mixed pickup-and-delivery trip changes load after each stop. A trip that fits at departure
can exceed the vehicle in the middle of the route, after a collection.

Checking only departure would pass a trip that is physically impossible.

:::

`BR-RTE-002` is a **warning**, deliberately. A half-empty vehicle is sometimes exactly right
— [customer commitments outrank utilisation](./planning-overview.mdx) — so it tells you and
lets you proceed.

## The frozen approved plan

Once approved, the plan's content is the **authorised version of the day**.

| Recorded | Meaning |
| --- | --- |
| **Approved By** | Who authorised it |
| **Approved At** | When |
| An approval row | On the **Approvals** tab |

The plan is not edited after approval. If the day changes, the change is made on the
**trip**, which carries its own approval and its own record.

:::note[Why the plan is not reopened]

Reopening an approved plan would mean the authorisation applied to something other than what
was authorised. Handling change at trip level keeps the record honest: the plan says what
was agreed, and the trips say what happened.

:::

## Modification is recorded, not prevented

A planner may change a recommendation before submitting it. What is required is a **reason**.

| Recorded | Where |
| --- | --- |
| The override reason | On the plan |
| The modification count | On the plan, and in Decision Quality |
| Who modified it | **Modified By** |
| **The original recommendation** | Preserved on the **Recommendation** tab |

:::info[The purpose is improvement, not policing]

[Decision Quality](../reporting/decision-quality.mdx) measures how often the recommendation
was accepted or overridden, and why.

A high override rate with one reason repeating is a signal about the *system*, not about the
planner. *Incorrect master data* appearing forty times is a data problem somebody can fix.

:::

## What to do when you are genuinely stuck

If a rule refuses something that must proceed, the answer is a **rule exemption** — not
switching the rule off.

| An exemption requires | Why |
| --- | --- |
| A **reason** | Somebody has to say why this is acceptable |
| A **risk** and a **mitigation** | Somebody has to have thought about it |
| An **approver** | Somebody has to own the decision |
| An **expiry date** | It cannot quietly become permanent |

The evaluation then records **Exception Applied**, not **Passed** — the rule did not pass,
it was waived.

:::warning[Separation of duties is not a candidate for exemption]

`BR-PLN-001` exists precisely so that no single person can authorise their own work. Waiving
it for convenience defeats the only control it provides.

If nobody is available to approve, the answer is a second approver, not an exemption.

:::

## Verify governance is working

| Test | Expect |
| --- | --- |
| Create a plan and try to approve it yourself | **Refused**, naming `BR-PLN-001` |
| Try the same as an Administrator | **Refused** |
| Have a second Operations Manager approve it | Succeeds |
| Check **Approved By** | The second person, not the author |
| Release a plan with an infeasible trip | **Refused**, naming `BR-PLN-002` and the trip |
