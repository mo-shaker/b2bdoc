## Before you start

| Requirement | Why |
| --- | --- |
| **Two user accounts** | The plan's author cannot approve it. A solo tester cannot finish the cycle |
| A **Planner** and an **Operations Manager** account | The whole cycle runs on operational roles; no administrator is needed at any step |
| A warehouse inside the pilot scope | SCOP only creates demand for operations a pilot-scope record has switched on |
| Odoo **Fleet / Administrator** and **Employees / Officer** for the planner | The planning wizard reads vehicles, and assigning a driver reads employees. *Fleet / Officer* is **not** enough — it carries a record rule limiting the user to vehicles they drive themselves |
| Odoo **Inventory / User** for the planner, and for whoever validates transfers | *Opening* a SCOP screen needs no Inventory rights. *Operating* a demand does: resolving ownership and marking it eligible refresh allocation from Odoo's own reservations. Validating a transfer is Odoo's own work |
| Stock on hand for the test products | So the transfer can reserve, and readiness can become plannable |
| A customer whose branch exists as a SCOP planning node | A destination without a node produces no demand — the reason is recorded as a `DemandGenerationSkipped` event |

## The checklist

| # | Role | Action | Expected result |
| --- | --- | --- | --- |
| 1 | Sales | Create a Sales Order for a customer that has a SCOP planning node | Quotation created |
| 2 | Sales | Confirm the Sales Order | Sales Order confirmed; Odoo creates the Delivery Order |
| 3 | Planner | `SCOP → Operations → Demands` | A Demand exists in **Draft**, referencing the delivery order. **Nobody created it by hand** |
| 4 | Planner | Open the demand, **Submit**, then **Validate** | **Refused** by `BR-INV-002` while ownership is unresolved — the rule and the products are named |
| 5 | Warehouse | Record the owner on the inventory itself | The stock now says who owns it |
| 5b | Planner | Press **Resolve Ownership** on the demand | Each line shows an owner and ownership source `stock_move_line` |
| 6 | Planner | **Validate**, then **Mark Eligible** | Demand reaches **Eligible for Planning** |
| 7 | Planner | `SCOP → Operations → Shipments` | A shipment **already exists**. Marking the demand eligible formed it — no button was pressed |
| 8 | Warehouse | Open the shipment, click **Stage Everything** | Readiness becomes **Ready**; evidence reads *"Everything is staged."* |
| 9 | Planner | `SCOP → Planning → Generate a Plan` — set the date, **Generate** | Planning Run **Recommended**; Daily Plan **Generated** with a recommended trip; no unplanned demand |
| 10 | Planner | Open the plan's trip and set the **Driver** | The trip carries a driver. The recommendation assigns a vehicle but never a driver |
| 11 | Planner | **Submit** the plan | Plan moves to **Under Review**, and so does its trip |
| 12 | Planner | As the plan's **author**, click **Approve** | **Refused** by `BR-PLN-001` — *"was created by you, so you may not approve it"* |
| 13 | Operations Manager | **Approve**, then **Release** | Plan **Approved** → **Released**; the trip follows; the demand reaches **Released**; Approved By and Approved At are filled |
| 14 | Warehouse | `SCOP → Operations → Loading Tasks` | One task per shipment on the trip, in **Pending**. **The release created them** |
| 15 | Warehouse | **Start** the task | Task **In Progress**; the trip moves to **Loading** |
| 16 | Warehouse | **Done** | Task **Done** with an actual duration; the trip reaches **Ready to Depart** |
| 17 | Driver | `SCOP → My Work → My Trips` | Only this driver's own trips are listed |
| 18 | Driver | Open the trip, **Depart** | Trip **In Progress**; shipment and demand both **In Execution** |
| 19 | Driver | Open the customer stop: **I have arrived**, then **Start unloading** | Stop **Servicing**, actual arrival stamped |
| 20 | Driver | Record proof of delivery — signature, photos | Attached to the stop |
| 21 | Driver | Press **Delivered** *before* the office has validated | **Refused**, and the message says the transfer is not validated yet — it does **not** call this a failed delivery |
| 22 | Warehouse | Validate the Delivery Order in Odoo | Transfer **Done**; the stop's Actual Qty now equals Planned Qty |
| 23 | Driver | Press **Delivered** | Stop **Completed**, outcome **Completed**, no reason required |
| 24 | — | Re-open the trip, shipment and demand | When the last stop closed, all three reached **Completed** on their own |
| 25 | Operations Manager | `SCOP → Reporting → Plan Coverage` | The plan shows **100.00** coverage |
| 26 | Operations Manager | `SCOP → Reporting → OTIF` | The delivery appears, in full and on time, against the captured commitment |
| 27 | Operations Manager | `SCOP → Reporting → Operation Timeline` | The whole operation can be reconstructed from its correlation reference |

## Negative tests worth running

These prove the controls work. Every one was re-run on `b2b` for this revision.

| Test | Expected refusal |
| --- | --- |
| Validate a demand whose ownership is unresolved | `BR-INV-002` — *required input is missing: ownership source on …* |
| Approve your own plan | `BR-PLN-001` — *was created by you, so you may not approve it. Separation of duties is the point of the approval step.* |
| Close a stop as **Could not deliver** with no reason | `BR-EXE-001` — *Record why stop N failed before closing it.* |
| Press **Delivered** before the office validates the transfer | *Stop N has no delivered quantity recorded yet. The warehouse validates the transfer in Odoo, and SCOP reads the result — wait for that, then close the stop.* SCOP does **not** call this a failed delivery |
| Press **Delivered** on a genuinely short delivery | *Stop N did not deliver everything planned, so it needs a reason before it can be closed.* |
| Edit an approved plan's date or objective profile | Refused — an approved plan is frozen |
| Modify a plan without an override reason | Refused — *what did you know that the recommendation did not?* |

## Behaviour that is expected, and is not a test failure

| You will see | Status |
| --- | --- |
| An **Operations Manager** cannot approve a plan they created themselves | Correct. `BR-PLN-001`, and it outranks administrator rights |
| **Loading Done** is refused while a loading task is open | Correct. A vehicle does not leave before its loading is recorded |
| A delivery to a customer with no SCOP planning node produces no demand | Correct, and recorded — look for `DemandGenerationSkipped` under `SCOP → Technical → Domain Events` |
| A demand with no service commitment is excluded from the OTIF on-time figure | Correct. It is counted separately; a delivery nobody promised a time for cannot be late |
| Operations carried over from a Release 1 database still show as incomplete | Expected. The upgrade does not rewrite the history of records left mid-flight — see [Release 1 Boundaries](./release-1-boundaries.mdx) |

:::note[The Release 1 workarounds are gone]

Earlier revisions of this checklist listed eight defects to expect — an empty Loading Tasks list, `Access Error` on the driver's **Depart**, **Create Shipment** and **Approve** refusing the roles that own them, a trip header with no buttons, `10000%` coverage, an empty OTIF and a crash on **Group By ▸ Status**.

All of them are fixed and covered by automated tests, and this revision re-confirmed each on `b2b`. If you meet any of them, that **is** a defect — raise it.

:::

## Recording your results

For each step record the reference, the expected result, the actual result, and a screenshot where it differs. Use **Operation Timeline** (`SCOP → Reporting → Operation Timeline`) to attach a single reconstructed history of the operation to your test evidence — it is assembled from the records rather than from recollection, which makes it the strongest evidence available.
