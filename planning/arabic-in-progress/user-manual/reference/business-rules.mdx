:::

## `BR-INV-002` — يجب أن تكون الملكية محلولةً ومتسقة {#br-inv-002}

| | |
| --- | --- |
| **الشدّة** | **حاجبة** |
| **النوع** | ملكية |
| **الموضوع** | الطلب |
| **تُطلَق عند** | `demand_validate` |
| **إن تعذّر تقييمها** | **حجب** |

### المعنى

يجب أن يكون لكل سطر طلب **مالكٌ محلول** بـ**مصدر ملكية** مُسجَّل، وألّا يخالف ذلك المالك ما سجّله Odoo على المخزون المحجوز.

### متى تُطلَق

حين يضغط مخطِّطٌ **Validate** على طلب.

### من يراها

**المخطِّط.** وهي أكثر القواعد التي تُصادَف بفارق كبير.

### ما تراه

<Screenshot
  src="quick-start/05-ownership-block-validate.png"
  alt="حوار رفض على نموذج الطلب في SCOP يفيد بوجوب حلّ الملكية قبل التحقق، ويسمّي الأسطر المتأثرة."
  caption="الرفض يسمّي القاعدة والسياسة والأسطر المخطئة بالضبط."
/>

### الرسالة حرفياً

أُعيد إنتاجها على `b2b` مقابل تحويل غير محجوز:

```text
This action is blocked by 1 business rule(s):
• BR-INV-002 v1.0: required input is missing:
  scop.demand.line.ownership_source on
  [QS-DEMO-01] QS Demo Chilled Box 10kg, [QS-DEMO-02] QS Demo Dry Goods Carton
```

ولاحظ أنها تسمّي **القاعدة ونسختها**، و**الحقل المفقود**، و**كل صنف مخطئ**.

### كيف تُعالَج

| # | جرّب |
| --- | --- |
| 1 | اضغط **Resolve Ownership**. فيُعيد الاشتقاق من المصادر الخمسة المعتمدة |
| 2 | إن كان التحويل غير محجوز، فاحجزه في Odoo ثم أعِد الاشتقاق |
| 3 | إن سجّل Odoo عدة مالكين مختلفين على حركة واحدة، فقسّمها ليكون لكل جزء مالك واحد |
| 4 | إن كان مخزون أمانة، فسِم الشريك ثم أعِد الاشتقاق |
| 5 | إن كان تسليماً بلا مالك مُسجَّل، فأثبِت من يملكه وسجّله في Odoo |

→ [تصحيح الملكية](../ownership/correcting-ownership.mdx)

### لماذا هي حاجبة

الملكية **لا تُفترَض للشركة أبداً**. ففي هذا النشر لا يؤكّد المالك الغائب شيئاً إطلاقاً، وقراءته ملكيةً للشركة كانت ستُسنِد إلى الشركة ملكية كل كرتونة مملوكة لعميل في المبنى — ثم كانت القاعدة ستؤكّد أن السلسلة متسقة داخلياً، لأنها ستكون كذلك فعلاً.

والخطأ المتسق هو الإخفاق الذي وُجدت هذه القاعدة لمنعه.

→ [ملكية المخزون](../ownership/inventory-ownership.mdx)

## `BR-PLN-001` — يجب فصل الاعتماد عن الإنشاء {#br-pln-001}

| | |
| --- | --- |
| **الشدّة** | **حاجبة** |
| **النوع** | اعتماد |
| **الموضوع** | الخطة اليومية |
| **تُطلَق عند** | `plan_approve` و`plan_release` |
| **إن تعذّر تقييمها** | **حجب** |

### المعنى

الشخص الذي **أنشأ** خطةً لا يستطيع **اعتمادها** ولا **إطلاقها**.

### متى تُطلَق

حين يضغط أحدهم **Approve** أو **Release** على خطة يومية.

### من يراها

**مدير العمليات**، و**مسؤول النظام**.

### ما تراه

<Screenshot
  src="quick-start/19-self-approval-refused.png"
  alt="حوار رفض يفيد بأن مُنشئ الخطة لا يستطيع اعتمادها، ويسمّي BR-PLN-001."
  caption="فصل المهام، يرفض مؤلف الخطة نفسه."
/>

### الرسالة حرفياً

أُعيد إنتاجها على `b2b` — **بحساب مسؤول النظام**، على خطة أنشأها مسؤول النظام:

```text
PLN-2026-09-01-01 was created by you, so you may not approve it.
Separation of duties is the point of the approval step.
```

### كيف تُعالَج

**يعتمدها مدير عمليات آخر.** ولا معالجة غيرها، ولا ينبغي أن تكون.

:::danger[هذه تعلو على الصلاحيات الإدارية]

مسؤول النظام يحمل كل مجموعة، ومنها مدير العمليات، ويستطيع اعتماد الخطط عموماً. ومع ذلك لا يستطيع اعتماد **خطةٍ أنشأها هو**.

فصل المهام ليس صلاحيةً يمكن أن تمنحها لنفسك.

:::

:::warning[فريقٌ من شخص واحد لا يستطيع إكمال دورة SCOP]

مقصودٌ لا سهو. فالتجربة تحتاج شخصين على الأقل يستطيعان الاعتماد.

:::

→ [حوكمة الخطة](../planning/plan-governance.mdx)

## `BR-PLN-002` — يجب ألّا تُطلَق رحلة محجوبة مع خطتها {#br-pln-002}

| | |
| --- | --- |
| **الشدّة** | **حاجبة** |
| **النوع** | تحقّق |
| **الموضوع** | الخطة اليومية |
| **تُطلَق عند** | `plan_release` |
| **إن تعذّر تقييمها** | **حجب** |

### المعنى

إن حملت أي رحلة على الخطة **نتيجةً حاجبة**، لم يمكن إطلاق الخطة.

### متى تُطلَق

حين يضغط مدير عمليات **Release** على خطة معتمَدة.

### من يراها

**مدير العمليات.**

### كيف تُعالَج

الرفض **يسمّي الرحلة المخطئة**.

| الخيار | كيف |
| --- | --- |
| أصلِح الرحلة | خفّف حمولتها، أو غيّر المركبة، أو أعِد ترتيب المحطات |
| أزِلها من الخطة | فتعود طلباتها إلى **Eligible for Planning** |

ثم أطلِق ثانيةً. ويمضي بقية اليوم طبيعياً.

### لماذا وُجدت

الخطة تُطلَق ككل. وبلا هذه القاعدة كانت رحلةٌ واحدة غير ممكنة ستدخل التشغيل إلى جانب الجيدة، وكان الإخفاق سيظهر عند رصيف التحميل بدل أن يظهر على الشاشة.

والسبب الكامن المعتاد هو `BR-RTE-001`.

## `BR-RTE-001` — يجب أن يكون التسلسل ممكناً عند كل نقطة {#br-rte-001}

| | |
| --- | --- |
| **الشدّة** | **حاجبة** |
| **النوع** | سعة |
| **الموضوع** | الرحلة |
| **تُطلَق عند** | `trip_approve` و`trip_release` و`load_confirm` |
| **إن تعذّر تقييمها** | **حجب** |

### المعنى

يجب أن تتّسع المركبة للحمولة عند **كل نقطة في تسلسل المحطات** — لا عند المغادرة فقط.

### لماذا «عند كل نقطة»

:::info[الرحلة المختلطة تُغيّر الحمولة بعد كل محطة]

فالمركبة التي تغادر المستودع داخل حدّها قد **تتجاوزه** في منتصف المسار، بعد استلام.

وفحص المغادرة وحدها كان سيُجيز رحلةً مستحيلة فعلياً.

:::

### متى تُطلَق

حين تُعتمَد رحلة أو تُطلَق، وحين تُؤكَّد حمولة.

### من يراها

**المخطِّط** و**مدير العمليات**.

### كيف تُعالَج

| # | الخطوة |
| --- | --- |
| 1 | اقرأ **First Breach Sequence** في رأس الرحلة — فهو يسمّي أين |
| 2 | افتح تبويب **Capacity** في الرحلة واقرأ **Breached Dimensions** |
| 3 | خفّف الحمولة، أو غيّر المركبة، أو أعِد ترتيب المحطات |
| 4 | اضغط **Compute Capacity**، ثم أعِد المحاولة |

→ [الرحلات](../execution/trips.mdx)

## `BR-RTE-002` — ينبغي ألّا يكون استغلال المركبة مهدِراً {#br-rte-002}

| | |
| --- | --- |
| **الشدّة** | **تنبيه** |
| **النوع** | سعة |
| **الموضوع** | الرحلة |
| **تُطلَق عند** | `trip_approve` و`trip_release` |
| **إن تعذّر تقييمها** | تسجّل وتمضي |

### المعنى

ينبغي ألّا تخرج مركبة فارغةً إلى حدٍّ كبير.

### تنبّه ولا تحجب

:::info[المركبة نصف الفارغة تكون أحياناً هي الصواب بالضبط]

الاستغلال هو **المرتبة السابعة** في ملف الأهداف. وتعهدات العملاء هي **المرتبة الثالثة**.

فترسل SCOP مركبةً نصف فارغة بدل أن تخلف وعداً، وتقول لك هذه القاعدة إن ذلك حدث دون أن توقفك.

→ [نظرة عامة على التخطيط](../planning/planning-overview.mdx)

:::

### من يراها

**المخطِّط** و**مدير العمليات**.

### كيف تُستجاب

التنبيه المفرد لا يحتاج إجراءً. أما التنبيهات **المستمرة** عبر رحلات كثيرة فإشارة حجم أسطول.

→ [استغلال المركبات](../reporting/vehicle-utilization.mdx)

## `BR-EXE-001` — يجب أن تحمل المحطة الفاشلة أو الجزئية سبب نتيجة {#br-exe-001}

| | |
| --- | --- |
| **الشدّة** | **حاجبة** |
| **النوع** | تحقّق |
| **الموضوع** | الرحلة |
| **تُطلَق عند** | `trip_complete` |
| **إن تعذّر تقييمها** | **حجب** |

### المعنى

كل محطة نتيجتها غير التسليم النظيف يجب أن تقول **لماذا**.

وتسري على التسليمات **الجزئية** كما على الإخفاقات الكاملة.

### متى تُطلَق

رسمياً، حين تكتمل **الرحلة**. وعملياً يُسأل السائق حين يُغلق **المحطة**، لأن تلك هي اللحظة الوحيدة التي يعرف فيها أحدٌ الجواب.

### من يراها

**السائق**، عند باب العميل.

### ما تراه

<Screenshot
  src="quick-start/34-failed-delivery-needs-reason.png"
  alt="رفض يفيد بأن المحطة الفاشلة تحتاج سبب نتيجة قبل إغلاقها."
  caption="يُسأل في اللحظة التي يستطيع السائق الإجابة فيها فعلاً."
  device="mobile"
/>

### كيف تُعالَج

اختر أحد أسباب نتيجة المحطة السبعة:

| السبب |
| --- |
| Customer location closed |
| Customer refused the delivery |
| Goods damaged in transit |
| Access to the location blocked |
| Ran out of time on the route |
| Vehicle issue |
| Rescheduled at the customer's request |

:::warning[لا تستخدم هذا لتحويل لم يُتحقَّق منه]

إن لم يُتحقَّق من تحويل Odoo بعد، أظهرت الكميات صفراً — ولم يُخفِق شيء. و SCOP تقول ذلك في رسالتها وتعرض المسارين.

→ [التسليم الفاشل](../execution/failed-delivery.mdx)

:::

## ماذا تفعل حين ترفضك قاعدة

| افعل | لا تفعل |
| --- | --- |
| اقرأ أي سجل يسمّيه الحوار | لا تعِد ضغط الزر نفسه |
| أصلِح ذلك السجل | لا تطلب إيقاف القاعدة |
| افحص `Governance → Rule Evaluations` للرسالة المخزَّنة | لا تفترض أنه خلل |
| حيث لا ينبغي أن تنطبق القاعدة فعلاً، اطلب **إعفاءً** | لا تُعلِّق القاعدة |

والإعفاء مفوَّض ومحدَّد المدة ويتطلب سبباً معلَناً وخطراً وتخفيفاً ومعتمِداً. ويسجّل التقييم عندئذٍ **Exception Applied** بدل التظاهر بأن القاعدة مرّت.

:::danger[BR-PLN-001 ليست مرشَّحةً للإعفاء]

فهي موجودة تحديداً كي لا يستطيع شخص واحد تفويض عمله هو. وتعطيلها للراحة يُبطِل الضابط الوحيد الذي توفّره.

فإن لم يتوافر أحد للاعتماد، فالجواب معتمِدٌ ثانٍ.

:::

## القواعد مُنسَّخة

لكل قاعدة **رمزٌ** ثابت و**نسخةٌ** متغيّرة. وهكذا تستطيع الإجابة عن *«ما كانت السياسة في مارس»* بلا تخمين — ولهذا تحتفظ تشغيلة التخطيط بسجل **Rules In Force** بما كان فعّالاً حين نُفِّذت.
