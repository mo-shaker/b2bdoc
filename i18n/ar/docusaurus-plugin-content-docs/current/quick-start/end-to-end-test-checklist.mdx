## قبل أن تبدأ

| المتطلب | السبب |
| --- | --- |
| **حسابا مستخدم** | مُعِدّ الخطة لا يستطيع اعتمادها، فلا يستطيع مختبِر واحد إتمام الدورة |
| مستودع داخل النطاق التجريبي | لا تُنشئ SCOP طلباً إلا للعمليات التي فعّلها سجل نطاق تجريبي |
| صلاحية Odoo **Inventory / User** لكل مختبِر، و**Fleet / Officer** للمخطِّط | شاشات SCOP تقرأ سجلات Odoo |
| مخزون متاح لمنتجات الاختبار | حتى يتمكن التحويل من الحجز وتصبح الجاهزية قابلة للتخطيط |
| عميل فرعه موجود كعقدة تخطيط في SCOP | الوجهة بلا عقدة لا تُنتج أي طلب، وبصمت |

## القائمة

| الخطوة | إجراء المختبِر | النتيجة المتوقعة |
| --- | --- | --- |
| 1 | أنشئ أمر بيع لعميل له عقدة في SCOP | تم إنشاء عرض السعر |
| 2 | أكّد أمر البيع | تأكّد أمر البيع، وأُنشئ أمر تسليم في Odoo |
| 3 | افتح `SCOP → Operations → Demands` | يوجد طلب بحالة **Draft** يشير إلى أمر التسليم |
| 4 | قدّم الطلب ثم اضغط **Validate** | **رفض** بالقاعدة `BR-INV-002` إذا كانت الملكية غير محسومة — مع ذكر القاعدة والمنتجات بالاسم |
| 5 | سجّل ملكية المخزون ثم اضغط **Resolve Ownership** | يُظهر كل بند مالكاً ومصدر ملكية `stock_move_line` |
| 6 | اضغط **Validate** ثم **Mark Eligible** | يبلغ الطلب حالة **Eligible for Planning** |
| 7 | اضغط **Create Shipment** | أُنشئت الشحنة، والجاهزية **Conditionally Ready** |
| 8 | اضغط **Stage Everything** على الشحنة | تصبح الجاهزية **Ready**، ونص الأدلة *«Everything is staged.»* |
| 9 | `SCOP → Planning → Generate a Plan` — حدّد التاريخ واضغط **Generate** | دورة تخطيط بحالة **Recommended**، وخطة يومية بحالة **Generated** مع رحلة موصى بها |
| 10 | افتح الخطة واضغط **Submit** | تنتقل الخطة إلى **Under Review** |
| 11 | بحساب **مُعِدّ الخطة نفسه**، اضغط **Approve** | **رفض** بالقاعدة `BR-PLN-001` — *«was created by you, so you may not approve it»* |
| 12 | بحساب **مستخدم آخر مخوّل**، اضغط **Approve** ثم **Release** | تبلغ الخطة **Approved** ثم **Released**، ويُعبَّأ حقلا Approved By وApproved At |
| 13 | على الرحلة: **Start Loading** ثم **Loading Done** | تبلغ الرحلة **Ready to Depart** |
| 14 | انطلق بالرحلة؛ وبحساب السائق: **I have arrived** ثم **Start unloading**، وسجّل إثبات التسليم | تبلغ المحطة **Servicing** مع تسجيل الوصول؛ ويُرفَق التوقيع والصور |
| 15 | اعتمد تحويل Odoo ثم اضغط **Delivered**؛ وراجع التقارير | تتطابق الكميات الفعلية مع المخططة؛ وتبلغ المحطة **Completed** بنتيجة **Completed**؛ وتظهر الخطة في **Plan Coverage** |

## اختبارات سلبية تستحق التنفيذ

هذه تثبت أن الضوابط تعمل. وقد جرى التحقق من الثلاثة الأولى على النظام الفعلي.

| الاختبار | الرفض المتوقع |
| --- | --- |
| التحقق من طلب لم تُحسم ملكيته | `BR-INV-002` — *required input is missing: ownership source on …* |
| اعتماد خطتك بنفسك | `BR-PLN-001` — *was created by you, so you may not approve it. Separation of duties is the point of the approval step.* |
| إغلاق محطة بـ **Could not deliver** بلا سبب | `BR-EXE-001` — *Record why stop N failed before closing it.* |
| الضغط على **Delivered** قبل اعتماد تحويل Odoo | *Stop N did not deliver everything planned, so it needs a reason before it can be closed.* |
| تعديل تاريخ خطة معتمدة أو ملف أهدافها | رفض — فالخطة المعتمدة مُجمَّدة |
| تعديل خطة بلا سبب تجاوز | رفض — *what did you know that the recommendation did not?* |

## سلوك معروف ليس فشلاً في الاختبار

لا تُسجِّل هذه كعيوب؛ فهي موثَّقة في [حدود الإصدار الأول](./release-1-boundaries.mdx).

| ما ستراه | الحالة |
| --- | --- |
| `SCOP → Operations → Loading Tasks` فارغة | لا يُنشئ أي مسار هذه السجلات في الإصدار الأول |
| زر **Depart** لدى السائق يُظهر `Access Error` | مشكلة معروفة — يجب أن يقوم مخطِّط أو مسؤول بانطلاق الرحلة |
| رفض **Create Shipment** للمخطِّط | مقصور حالياً على المسؤول |
| رفض **Approve** لمدير العمليات | يتطلب حالياً صلاحية SCOP Administrator |
| رأس الرحلة لا يعرض أزرار دورة الحياة | يُعرض نموذج السائق المبسَّط لجميع الأدوار |
| تغطية الخطة تُظهر `10000%` | مشكلة عرض فقط؛ والأعداد صحيحة |
| عملية تسليم مكتملة لا تظهر في OTIF | دورتا حياة الطلب والشحنة لا تتقدمان أثناء التنفيذ |
| تجميع قائمة SCOP بحسب **Status** يُظهر خطأً | مشكلة معروفة في مساعد تجميع الحالات |

## تسجيل نتائجك

سجّل لكل خطوة المرجع والنتيجة المتوقعة والنتيجة الفعلية، مع صورة للشاشة عند الاختلاف. واستخدم **Operation Timeline** (`SCOP → Reporting → Operation Timeline`) لإرفاق تاريخ واحد مُعاد بناؤه للعملية ضمن أدلة الاختبار — فهو مُجمَّع من السجلات لا من الذاكرة، وهذا يجعله أقوى دليل متاح.
