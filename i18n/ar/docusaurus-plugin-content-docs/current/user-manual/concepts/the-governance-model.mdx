القواعد المفردة مسرودة في [قواعد العمل](../reference/business-rules.mdx). وهذه الصفحة تشرح الآلية التي تعمل داخلها.

## الفكرة

لا تعتمد SCOP على تذكّر الناس للسياسة. فالسياسة **مُسجَّلة كبيانات**، وتُقيَّم في **لحظة محددة**، والتقييم **يُحفظ**.

وينتج عن ذلك ثلاث خصائص تستحق الاقتناء:

| الخاصية | الأثر |
| --- | --- |
| الرفض يسمّي القاعدة | لا يُقال لك *«غير مسموح»* وحدها أبداً |
| كل فحص مُسجَّل | تستطيع إثبات أن قاعدة طُبِّقت أو لم تُطبَّق |
| القواعد مُصدَّرة | تستطيع أن تقول أي سياسة كانت سارية في مارس |

## قواعد العمل

`SCOP → Governance → Business Rules`

قاعدة العمل سياسة واحدة معتمدة ومُصدَّرة. وستٌّ منها سارية في الإصدار الأول.

| الحقل | المعنى |
| --- | --- |
| **Code** | مفهوم العمل المستمر — `BR-INV-002` |
| **Version** | مراجعة معتمدة منه |
| **Name** | السياسة في جملة |
| **Domain** | أي جزء من العملية تنتمي إليه |
| **Type** | نوع القاعدة — تحقّق أو ملكية أو اعتماد أو سعة |
| **Severity** | مدى شدّتها |
| **Subject** | الكائن الذي تسري عليه |
| **Fires at** | البوابة أو البوابات التي تُقيّمها |
| **If unable to evaluate** | ماذا يُفعل حين يتعذّر إجراء الفحص نفسه |
| **Status** | القواعد **Active** وحدها هي المفروضة |

و**رمز** القاعدة ثابت؛ و**الإصدار** يتغير حين تتغير السياسة. وهكذا تجيب عن *«ما كانت القاعدة في مارس»* دون تخمين.

### الشدّة

| الشدّة | الأثر عند فشل القاعدة |
| --- | --- |
| **Information** | يُسجَّل. ولا شيء يُحجب |
| **Warning** | يُسجَّل ويُعرض. ويستمر الإجراء |
| **Approval Required** | يحتاج الإجراء اعتماداً مُصرَّحاً به |
| **Blocking** | يُرفض الإجراء |
| **Critical** | يُرفض، ويُعامَل كحدث خطير |

وخمس من قواعد الإصدار الأول الست **حاجبة**. وواحدة — `BR-RTE-002` استغلال المركبة — **تحذير**، وهذا مقصود.

### إن تعذّر تقييم القاعدة

قد يتعذّر إجراء الفحص — لنقص بيانات أو تعذّر اعتمادية. وتذكر كل قاعدة مسبقاً ما ينبغي حينها:

| الإعداد | المعنى |
| --- | --- |
| **Treat as blocking** | ارفض. يُستخدم حيث يكون المضي بلا فحص غير مقبول |
| **Treat as a warning** | حذّر واستمر |
| **Record and continue** | سجّل وامضِ |

و`BR-INV-002` و`BR-PLN-001` و`BR-PLN-002` و`BR-RTE-001` و`BR-EXE-001` كلها **تحجب** إن تعذّر تقييمها. فعدم معرفة مالك البضائع يُعامَل تماماً كمعرفة أن الملكية خاطئة.

## البوابات — لحظة إطلاق القاعدة

لا تُقيَّم القاعدة عند كل حفظ. بل تُطلَق عند **بوابة** مُسمّاة، وهي لحظة محاولة إجراء.

| البوابة | تُطلَق حين | القواعد |
| --- | --- | --- |
| `demand_validate` | يُتحقَّق من طلب | `BR-INV-002` |
| `demand_eligible` | يُؤهَّل طلب | — |
| `plan_approve` | تُعتمد خطة | `BR-PLN-001` |
| `plan_release` | تُطلَق خطة | `BR-PLN-001` و`BR-PLN-002` |
| `trip_approve` | تُعتمد رحلة | `BR-RTE-001` و`BR-RTE-002` |
| `trip_release` | تُطلَق رحلة | `BR-RTE-001` و`BR-RTE-002` |
| `load_confirm` | تُؤكَّد حمولة | `BR-RTE-001` |
| `trip_depart` | تغادر رحلة | — |
| `trip_complete` | تكتمل رحلة | `BR-EXE-001` |
| `stop_complete` | تكتمل محطة | — |

ولهذا يُحفظ الطلب الذي سيفشل في التحقق — فالقاعدة تُطلَق حين تضغط **Validate**، لا حين تكتب.

## تقييمات القواعد — سجل كل فحص

`SCOP → Governance → Rule Evaluations`

كلما أُطلقت بوابة، كُتب الجواب.

| النتيجة | المعنى |
| --- | --- |
| **Not Applicable** | القاعدة لا تسري على هذا السجل |
| **Passed** | نجح الفحص |
| **Failed — Warning** | فشل، لكنه غير حاجب |
| **Failed — Approval Required** | يحتاج اعتماداً مُصرَّحاً به للمضي |
| **Failed — Blocking** | رُفض |
| **Exception Applied** | كان إعفاء معتمد سارياً |
| **Unable to Evaluate** | تعذّر الفحص؛ وقرّر إعداد القاعدة نفسها ما حدث |
| **Suspended** | كانت القاعدة معلَّقة، فلم يُجرَ الفحص |

ويسجّل كل تقييم كذلك **الرسالة** المعروضة للمستخدم، والقيمتين **المقيسة** و**الحدّية** حيث تكون القاعدة عددية، و**الدليل** خلف الجواب.

<Screenshot
  src="user-manual/27-rule-evaluations.png"
  alt="قائمة تقييمات القواعد في SCOP تعرض الفحوص المُسجَّلة برمز القاعدة والنتيجة والموضوع والرسالة."
  caption="كل بوابة أُطلقت، بجوابها. وهنا يُفسَّر الرفض بعد اختفاء نافذته."
/>

وهذه الشاشة تُفتح حين يقول أحدهم *«حجبتني SCOP ولا أعرف لماذا»* — فتجد سجله وتقرأ التقييم، والرسالة محفوظة حرفياً.

:::info[الحوكمة ظاهرة عند النجاح كما عند الرفض]

**مُتحقَّق منه على `b2b`** بعد اعتماد مدير عمليات لخطة أنشأها مسؤول النظام وإطلاقها:

| القاعدة | البوابة | النتيجة | الرسالة |
| --- | --- | --- | --- |
| `BR-PLN-001` | `plan_approve` | نجحت | *Approval is separated from creation.* |
| `BR-PLN-001` | `plan_release` | نجحت | *Approval is separated from creation.* |
| `BR-PLN-002` | `plan_release` | نجحت | *No trip on this plan carries a blocking finding.* |
| `BR-RTE-001` | `trip_approve`، `trip_release` | نجحت | *Feasible at every point of the sequence.* |
| `BR-RTE-002` | `trip_approve`، `trip_release` | **فشل — تحذير** | *Peak utilisation is only 0.0%, below the 50% the plan aims for.* |

ولاحظ الصف الأخير: أُطلقت الخطة **طبيعياً** مع بقاء تحذير الاستغلال قائماً عليها. وهذا `BR-RTE-002` يتصرف كما صُمِّم تماماً. ولاحظ كذلك أن `BR-PLN-001` يُقيَّم **مرتين** — عند الاعتماد وعند الإطلاق.

:::

## إعفاءات القواعد — التنازل المُصرَّح به

`SCOP → Governance → Rule Exemptions` *(المخطِّط فما فوق)*

أحياناً يجب التنازل عن قاعدة لحالة بعينها. وتوفّر SCOP طريقة مضبوطة لذلك، فيكون قراراً لا التفافاً.

| الحقل | الغرض |
| --- | --- |
| **Rule** | أي قاعدة يُتنازَل عنها |
| **Type** | One-Time · Time-Bound · Scope-Bound · Emergency · Policy Exception |
| **Subject** | أي سجل، حيث لا يكون التنازل عاماً |
| **From / To** | **إلزامي.** فالإعفاء ينتهي دائماً |
| **Reason** | **إلزامي.** لماذا هذا مقبول |
| **Risk** و**Mitigation** | ما قد يسوء، وما يُفعل حياله |
| **Requested by / Approved by** | من طلب، ومن وافق |
| **Status** | Draft · Approved · Expired · Revoked |

ولا أثر إلا لإعفاء **Approved** داخل تواريخه. وحين يسري، يسجّل التقييم **Exception Applied** بدل التظاهر بنجاح القاعدة.

:::warning[الإعفاء ليس كتعليق القاعدة]

تعليق القاعدة يوقفها للجميع، ويسجّل كل تقييم بعدها **Suspended**. أما الإعفاء فيتنازل عن قاعدة واحدة لنطاق واحد ولمدة معلومة، بمُعتمِد مُسمّى ومخاطرة مُسجَّلة.

فإن كنت تمدّ يدك إلى التعليق لتحريك سجل واحد، فأنت تريد إعفاءً.

:::

## صلاحيات الاعتماد — من يحقّ له التصرف

`SCOP → Governance → Approval Authorities` *(مسؤول النظام)*

حقوق الوصول تقول من يستطيع *فتح* شاشة. وصلاحية الاعتماد تقول من يحقّ له *أداء إجراء*. وهما منفصلتان عمداً.

<Screenshot
  src="user-manual/30-approval-authorities.png"
  alt="قائمة صلاحيات الاعتماد في SCOP تعرض أي مجموعة يجوز لها أي إجراء على أي كائن، وأين يُمنع الاعتماد الذاتي."
  caption="الصلاحيات المُهيّأة على b2b. صفّا الخطة وحدهما يمنعان الاعتماد الذاتي."
/>

| الكائن | الإجراء | المجموعة | يُمنع الاعتماد الذاتي |
| --- | --- | --- | --- |
| الخطة اليومية | approve | Operations Manager | **نعم** |
| الخطة اليومية | release | Operations Manager | **نعم** |
| الرحلة | approve | Operations Manager | لا |
| الرحلة | release | Operations Manager | لا |
| الرحلة | depart | Planner / Dispatcher | لا |
| الرحلة | cancel | Planner / Dispatcher | لا |
| الطلب | plan وreplan وcancel | Planner / Dispatcher | لا |
| الشحنة | cancel | Planner / Dispatcher | لا |
| الحمولة | cancel | Warehouse User | لا |

وعلامة **Forbid Self-Approval** هي ما يُنفِّذ فصل المهام للخطط. وتُفرَض مهما بلغ عدد المجموعات التي يحملها المستخدم.

:::danger[فصل المهام يعلو على الصلاحيات الإدارية]

يحمل مسؤول النظام مجموعة مدير العمليات ويستطيع اعتماد الخطط عموماً. ومع ذلك لا يستطيع اعتماد **خطة أنشأها**. فـ`BR-PLN-001` ليست صلاحية تمنحها لنفسك.

:::

## رموز الأسباب — تفسيرات مضبوطة

`SCOP → Governance → Reason Codes`

حيث تسأل SCOP *لماذا*، تعرض قائمة لا مربع نص حر. واحد وخمسون سبباً في ست فئات.

| الفئة | العدد | تصادفها حين |
| --- | --- | --- |
| **Unplanned Demand** | 12 | تقرأ لماذا لم يُخطَّط طلب |
| **Override** | 9 | تعدّل خطة موصى بها |
| **Exception Root Cause** | 11 | تصنّف استثناءً |
| **Stop Outcome** | 7 | تُفشل محطة أو تتخطاها |
| **Next Action** | 7 | تسجّل ما يُفعل بطلب غير مخطَّط |
| **Return Disposition** | 5 | تقرّر مصير بضائع عائدة |

والمفردات المضبوطة هي ما يجعل *«لماذا نُخفق في التسليم باستمرار»* سؤالاً يجيب عنه تقرير بدل قراءة مئة صندوق تعليق.

→ [رموز الأسباب](../reference/reason-codes.mdx)

## ملفات الأهداف — ما يُحسِّن التخطيط تجاهه

`SCOP → Governance → Objective Profiles` *(المخطِّط)*

لا يُحسِّن التخطيط رقماً واحداً. بل يعمل نزولاً في **قائمة مرتَّبة**، ولا يُقايَض هدف أدنى بهدف أعلى أبداً.

| الرتبة | الهدف |
| --- | --- |
| 1 | السلامة والقانون والملكية والامتثال الإلزامي |
| 2 | الجدوى |
| 3 | التزامات العملاء الإلزامية |
| 4 | الأولوية وحماية الخدمة |
| 5 | تغطية الطلب |
| 6 | توفّر الموارد |
| 7 | استغلال السعة |
| 8 | كفاءة المسافة والوقت والتكلفة |
| 9 | التفضيلات التشغيلية |

ولهذا تترك SCOP مركبة نصف فارغة بدل خرق التزام: الاستغلال في الرتبة 7 والالتزامات في الرتبة 3.

→ [نظرة عامة على التخطيط](../planning/planning-overview.mdx)

## قراءة الرفض

حين تحجبك قاعدة، تسمّي النافذة القاعدة، وتذكر السياسة بالكلمات، وتسرد الدليل — عادةً السجلات المخالفة بالضبط.

| افعل | لا تفعل |
| --- | --- |
| اقرأ أي سجل سُمِّي | إعادة الضغط على الزر نفسه |
| أصلِح ذلك السجل | طلب إيقاف القاعدة |
| حيث لا ينبغي أن تسري القاعدة فعلاً، اطلب **إعفاءً** | افتراض أنه خلل |
